Software Requirements Specification (SRS)
Project: Real-Time Weather Data Platform
Version: 1.1
Date: 2026-03-27
Prepared by: Data Platform Team

1. Introduction
1.1 Purpose
This SRS defines functional and non-functional requirements for the current implementation of the Real-Time Weather Data Platform. The system ingests weather data from OpenWeatherMap, stores raw payloads in a lake layer, transforms data into partitioned Parquet staging datasets, and loads analytics tables into PostgreSQL.

1.2 Scope
In scope (current roadmap):
- Run scheduled, multi-city ingestion workflows
- Ingest current weather and 5-day forecast data
- Store raw JSON in a local or S3-compatible data lake
- Produce clean staging Parquet datasets
- Load analytics tables into PostgreSQL
- Support dashboarding through external BI tools

Out of scope (future expansion):
- Weather alerts ingestion
- Real-time ingestion (<5 minute frequency)
- ML-based anomaly detection
- PostGIS spatial processing
- Public-facing REST API

1.3 Definitions
- Data Lake: Object storage containing raw and staged data (JSON/Parquet)
- Lakehouse: Architecture combining data lake and analytics warehouse layers
- Raw Layer: Unmodified JSON API responses
- Staging Layer: Cleaned and normalized Parquet partitions
- Analytics Layer: PostgreSQL tables optimized for query and BI
- DAG: Directed Acyclic Graph workflow (future Airflow/Prefect target)

2. Overall System Description
The platform follows a practical lakehouse architecture:
- Raw API responses in lake storage
- Python ETL modules for extract, transform, and load
- Parquet staging for reproducibility and reload capability
- PostgreSQL analytics layer for downstream querying
- Current orchestration through CLI + GitHub Actions schedules

Current data sources:
- Current weather endpoint (`/weather`)
- Forecast endpoint (`/forecast`)

Deferred data source:
- Alerts endpoint (`/onecall`) moved to future expansion due free-tier API limitations

3. Functional Requirements
3.1 Extraction Requirements
FR-1: Ingest data from OpenWeatherMap endpoints:
- `/weather` (current weather)
- `/forecast` (5-day, 3-hour intervals)

FR-2: Support ingestion for multiple cities loaded from the `cities` table.

FR-3: Write raw JSON API responses into the data lake:
- `data_lake/raw/{data_type}/{city}/{year}/{month}/{day}/{timestamp}.json`

FR-4: Continue processing remaining cities if one city/API call fails.

FR-5: Retry failed API calls with exponential backoff (planned enhancement).

3.2 Transformation Requirements
FR-6: Normalize weather attributes (temperature, pressure, humidity, wind, weather text).

FR-7: Standardize timestamps in UTC in staging and analytics tables.

FR-8: Produce tabular outputs for:
- `weather_history`
- `weather_forecast`

FR-9: Store transformed data as partitioned Parquet files:
- `data_lake/staging/{data_type}/city={city}/year={YYYY}/month={MM}/data.parquet`

FR-10: Prevent duplicates in staging merges using deterministic keys.

3.3 Loading Requirements
FR-11: Load clean data into PostgreSQL tables:
- `weather_history`
- `weather_forecast`
- `cities` (reference)

FR-12: Use bulk operations (`executemany` now, COPY acceptable future optimization).

FR-13: Preserve historical data (append-only behavior).

FR-14: Ensure idempotent loads on retries (DB constraints + conflict handling).

3.4 Orchestration Requirements
FR-15: Support scheduled execution for both current and forecast pipelines.

FR-16: Log run progress and failures.

FR-17: Add run-level metrics (row counts, durations) as future enhancement.

3.5 Monitoring Requirements
FR-18: Detect malformed or missing required fields in transform stage (partially implemented).

FR-19: Detect stale data and schema drift (planned).

FR-20: Detect row count anomalies by city and data type (planned).

4. Non-Functional Requirements
- Scalability: Support dozens of cities and large historical datasets
- Performance: Keep ETL runtime practical for free-tier compute targets
- Reliability: Robust error handling, retries for transient failures (planned)
- Security: Secrets from environment variables or CI secrets
- Cost Efficiency: Favor free-tier services and minimal operational overhead
- Extensibility: Add new data sources without redesigning storage/load architecture

5. Data Dictionary
5.1 `cities`
- Stores metadata for tracked cities and API mapping fields.

5.2 `weather_history`
- Current weather observations with UTC timestamp and weather metrics.

5.3 `weather_forecast`
- Forecast observations including `forecast_timestamp` and `forecast_horizon`.

5.4 Deferred Table (`weather_alerts`)
- Table exists as exploratory schema, but population is deferred to future expansion.

6. ETL Workflow Specification
6.1 Extract
1. Load cities from PostgreSQL.
2. Call `/weather` or `/forecast` for each city.
3. Persist raw JSON payloads to raw layer.

6.2 Transform
1. Read raw files incrementally using per-partition high-water marks.
2. Convert raw JSON into staging records.
3. Merge with existing staging files and deduplicate.
4. Write Parquet outputs and update high-water marks.

6.3 Load
1. Read staging partitions.
2. Map city names to city IDs.
3. Insert into PostgreSQL with `ON CONFLICT DO NOTHING`.

7. Acceptance Criteria (Current Scope)
- Current and forecast pipelines run on schedule.
- Raw, staging, and analytics layers are populated for supported data types.
- No duplicate records for uniqueness keys in analytics tables.
- Test suite passes in CI.

10. Architectural Decisions (Recorded)
AD-1: Keep weather alerts out of current scope until a suitable free alert source is available.

AD-2: Use modular Python files (`extract.py`, `staging_transform.py`, `load.py`) instead of a monolith.

AD-3: Use repository pattern in `storage.py` to support local and R2 backends with the same interface.

AD-4: Use Parquet staging + high-water marks for reproducible, incremental processing.

AD-5: Enforce idempotency with DB uniqueness constraints and conflict-safe inserts.

AD-6: Use GitHub Actions schedules now; keep Airflow/Prefect as future orchestration upgrade.
